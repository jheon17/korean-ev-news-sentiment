# 5단계: 사람이 만든 정답 데이터

## 1. 목적

모델을 평가하려면 사람이 직접 붙인 정답 라벨이 필요하다.

이번 단계에서는 전처리된 뉴스 35건을 라벨링할 수 있는 CSV 파일로 만들고,
사람이 `긍정`, `중립`, `부정` 중 하나를 직접 입력한다.
현재는 35건의 최초 라벨링과 전체 수동 재검토까지 완료했다.

## 2. 쉬운 개념 설명

모델이 뉴스 감성을 분류하더라도, 그 결과가 맞는지 판단할 기준이 필요하다.
이 기준이 사람이 만든 정답 데이터다.

예를 들어 어떤 모델이 한 뉴스를 `긍정`이라고 예측했을 때,
사람이 만든 정답 라벨도 `긍정`이면 맞은 것이다.
사람이 만든 정답이 `중립`이면 틀린 것이다.

그래서 라벨링 기준을 먼저 정하고, 사람이 직접 일관되게 라벨을 붙이는 과정이 중요하다.

## 3. 사용자가 먼저 생각할 질문

1. 제목과 요약문만 보고 국내 전기차 시장 전체에 미칠 영향을 판단할 수 있는가?
2. 판단 근거가 부족한데 억지로 긍정이나 부정을 고르고 있지는 않은가?
3. 최종 테스트용 라벨을 나중에 프롬프트 수정이나 규칙 수정에 사용하지 않을 수 있는가?

## 4. 최소 실행 코드

아래 명령으로 라벨링용 CSV 파일을 만든다.

```powershell
uv run python src/create_labeling_dataset.py
```

출력 파일은 다음 위치에 생성된다.

```text
data/labels/news_labeling_sample_20260803.csv
```

## 5. 라벨링 파일 구조

라벨링 CSV에는 다음 열이 들어 있다.

| 열 이름 | 의미 |
| --- | --- |
| article_id | 기사 식별자 |
| split | 개발용 또는 최종 테스트용 구분 |
| gold_label | 사람이 직접 입력할 정답 라벨 |
| label_reason | 라벨을 선택한 이유 |
| ambiguous_note | 애매한 점이 있을 때 적는 메모 |
| search_query | 처음 수집된 검색어 |
| matched_queries | 같은 기사가 함께 잡힌 검색어 |
| duplicate_count | 중복 수집 횟수 |
| title | 전처리된 제목 |
| description | 전처리된 요약문 |
| originallink | 원문 링크 |
| link | 네이버 뉴스 링크 또는 기사 링크 |
| pubDate_iso | 통일된 발행일 |

## 6. 라벨 입력 규칙

`gold_label`에는 반드시 다음 세 값 중 하나만 입력한다.

- 긍정
- 중립
- 부정

`label_reason`에는 왜 그렇게 판단했는지 짧게 적는다.

예시는 다음과 같다.

- 충전소 확대라서 전기차 이용 편의성이 좋아질 가능성이 있음
- 특정 기업 행사 소개라 시장 전체 영향은 불명확함
- 화재 사고라 소비자 신뢰 하락 가능성이 있음

`ambiguous_note`는 애매하지 않으면 비워둬도 된다.
애매한 경우에는 어떤 점이 애매했는지 적는다.

## 7. 개발용과 최종 테스트용 분리

초기 설계에서 `split` 열은 다음 두 값 중 하나로 나눴다.

- dev: 라벨 기준, 규칙 기반 모델, 프롬프트를 수정할 때 볼 수 있는 데이터
- final_test: 마지막 평가에만 사용할 데이터

초기 설계에서는 최종 테스트용 데이터를 모델이나 프롬프트를 고치는 과정에서 보지 않아
평가 결과가 실제보다 좋아 보이는 데이터 누수를 막으려고 했다.

이번 샘플 35건은 다음처럼 나눈다.

- dev: 28건
- final_test: 7건

이후 전체 수동 재검토 과정에서 기존 final_test의 내용도 확인했고,
dev와 final_test에 같은 사건을 다룬 유사 기사가 섞인 점도 발견했다.
따라서 split 값은 추적용으로 남기되 기존 final_test는 앞으로 최종 블라인드 테스트로 사용하지 않는다.

## 8. 결과 해석 방법

라벨링이 끝나면 먼저 `gold_label`이 비어 있는 행이 없는지 확인한다.

그다음 라벨 개수를 확인한다.
한 라벨에 너무 치우쳐 있으면 검색어 구성이 편향되었을 가능성이 있다.

`ambiguous_note`가 많은 경우에는 라벨 가이드가 아직 모호하다는 뜻일 수 있다.
초기 설계에서는 개발용 데이터의 애매한 사례만으로 라벨 가이드를 수정할 계획이었다.
현재는 기존 final_test까지 수동 검토했으므로, 다음 평가에는 별도의 새 블라인드 데이터를 사용해야 한다.

## 9. 오류, 편향, 데이터 누수 가능성

제목과 요약문만으로 판단하면 본문 맥락을 놓칠 수 있다.

라벨링하는 사람이 이미 특정 결론을 기대하면 라벨이 한쪽으로 치우칠 수 있다.

블라인드 테스트용 라벨을 보면서 규칙이나 프롬프트를 수정하면 데이터 누수가 생긴다.
기존 final_test는 이미 검토했으므로 다음 최종 평가에는 재사용하지 않는다.

애매한 사례를 무리하게 긍정이나 부정으로 넣으면 모델이 과감한 오판을 배우기 쉽다.
근거가 부족하면 중립을 우선 고려한다.

## 10. 완료 조건

초기 5단계는 다음 조건을 만족하면 완료되는 것으로 설계했다.

- 라벨링용 CSV 파일이 생성되어 있다.
- 각 기사에 article_id가 있다.
- 개발용과 최종 테스트용이 split 열로 분리되어 있다.
- gold_label에는 긍정, 중립, 부정 중 하나를 입력할 수 있다.
- 애매한 이유를 ambiguous_note에 기록할 수 있다.
- 최종 테스트용 데이터는 규칙이나 프롬프트 수정에 사용하지 않기로 한다.

이후 기존 split의 사건 중복과 검토 이력을 확인했으므로,
새 평가 데이터에서는 같은 사건을 분리하고 블라인드 상태를 유지해야 한다.

## 11. 실행 확인 결과

2026년 8월 3일에 라벨링용 CSV 파일을 생성했다.

- 입력 파일: `data/processed/naver_news_sample_20260803_preprocessed.csv`
- 출력 파일: `data/labels/news_labeling_sample_20260803.csv`
- 입력 기사 수: 35건
- 출력 기사 수: 35건
- 개발용(dev) 기사 수: 28건
- 최종 테스트용(final_test) 기사 수: 7건

35건의 라벨링을 완료한 뒤 전체 기사를 다시 수동 검토했다.

현재 전체 라벨 분포는 다음과 같다.

| 구분 | 긍정 | 중립 | 부정 | 합계 |
| --- | ---: | ---: | ---: | ---: |
| dev | 11 | 17 | 0 | 28 |
| 기존 final_test | 0 | 6 | 1 | 7 |
| 전체 | 11 | 23 | 1 | 35 |

데이터 품질 확인 결과는 다음과 같다.

- 빈 `gold_label`: 0건
- 허용되지 않은 `gold_label`: 0건
- 빈 `label_reason`: 0건

기존 final_test는 수동 검토 과정에서 내용을 확인했고 dev와 같은 사건의 기사도 포함돼 있었다.
초기 분리 과정은 학습 기록으로 남기지만, 이 7건은 앞으로 최종 블라인드 테스트로 사용하지 않는다.
